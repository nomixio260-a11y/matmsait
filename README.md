# トピあつめ（matmsait）

複数サイトの RSS フィードから新着記事の **見出し・短い抜粋・元記事リンク** を集めて一覧表示する、まとめ（アンテナ）サイトです。
GitHub Actions で 1 時間ごとに収集・ビルドし、静的サイトとして **Cloudflare Pages**（pages.dev）に公開します（サーバー費 0 円）。
「いま何が話題なのか一瞬で分かる」ことを目指し、同じ出来事を報じたメディアの数・新しさ・分野の広がりから計算する**話題度スコア**、3時間で報じるメディアが増えた**急上昇**、話題ごとに各メディアの報道を報じた順に比べられる**話題のページ**（初報・報道の広がりのグラフ）、**今日の重要ニュース**、**注目ワード**、**メディア別**（初報の数）、AI・Apple・MLB などの**タグ**（AI ニュースランキング）を備えています。運営者が作る AI 要約は「10秒で読む・30秒で読む・2分で理解」で読めます。記事検索、あとで読む、広告枠（Google AdSense）、ホーム画面への追加（PWA・オフライン表示）もあります。
アクセス解析（訪問者数・いま見ている人数・よく読まれている記事など）も、Cloudflare の無料プランで同じドメインの `/api` で動きます（下の「アクセス解析」）。
読者は気になるジャンル・掲載元・キーワードをフォローして新着をまとめて見られ、ブラウザの通知（プッシュ通知）でも受け取れます（下の「フォロー・通知（読者向け）」）。管理画面には、サイトの状態とやることをまとめた「概要」、編集部のピックアップ・お知らせ、通知の管理もあります（下の「管理画面のページ」）。

公開URL: https://topiatsume.pages.dev/ （2026-10-07 に GitHub Pages から移転。以前の https://nomixio260-a11y.github.io/matmsait/ は新しい URL への転送ページになります）

開発・テスト・毎時の収集とビルドは GitHub（このリポジトリと GitHub Actions）で行い、公開するサイトとアクセス解析のサーバーは Cloudflare に置きます（下の「公開先（Cloudflare）」）。

> **開発を引き継ぐ方へ**: 開発の経緯・現在の状態・未解決の課題は [`docs/DEVLOG.md`](docs/DEVLOG.md)（開発記録）にまとめています。
> 開発（コード・設定の変更）をしたら、必ず同ファイルに記録を追記してください（詳しくは下の「開発記録・引き継ぎ」）。

## 仕組み

```
sources.yaml ─▶ scripts/fetch-feeds.ts ─▶ data/items.json ─▶ Astro でビルド ─▶ Cloudflare Pages（pages.dev）
 (収集元一覧)    (取得・整形・重複排除)     (直近30日/最大12000件)   (静的HTML)       ＋ /api（アクセス解析）
```

- 記事本文・画像は転載しません。抜粋は約 120 文字で切り詰め、全文は元サイトへ誘導します。
- 同じ記事（URL が同じもの）は 1 件にまとめます。
- URL が違っても見出しが同じ記事（Yahoo!ニュースなどへの転載、スマホ版の URL など）は 1 件にまとめ、元の配信元の記事を残します。
- 抜粋がタイトルの繰り返しやページ部品の断片になっている場合は取り除きます。
- **話題のニュース**: 見出しの似ている記事を「同じ出来事の報道」としてまとめます（`src/lib/related.ts` の `clusterTopics`）。同じ掲載元どうしはまとめず、まれな言葉を共有しているときだけ同じ話題とみなします。話題ごとに次の数字を計算します（`src/lib/topic-core.ts`・`src/lib/topics.ts`。計算のしかたはサイトの about の「話題度スコア・急上昇の計算のしかた」にも書いています）。
  - 報じたメディアの数（「N社が報道」）・初報（いちばん早く報じたメディア）・直近1/3/24時間に新しく報じたメディアの数
  - **話題度スコア**（0〜100）: 報道1件ごとに1（報じてから12時間ごとに半分）を足し、報じたメディアの分野が多いほど・このサイトでよく読まれたほど上乗せ
  - **急上昇**: 直近3時間に新しく報じたメディアの多い順（少ない時間帯は6・12時間に広げる）。最初の報道から6時間以内の話題は NEW
  - **今日の重要ニュース**: 24時間の報道の数と分野の広がりの順（分野ごとに件数の上限）
  - **注目ワード**: 24時間の見出しで、それまでの6日より急に増えた言葉（候補は AI 要約のキーワードとタグの言葉）
  - **メディア別**: 24時間に話題になったニュースを報じた数と初報の数
- **話題のページ**（`/topic/<最初の記事のID>/`）: 2社以上が報じた話題ごとに、各メディアの見出しを報じた順に並べて比べられるページ（初報の印・初報からの時間・報道の広がりのグラフ・AI 要約・関連する話題）。記事の「N社が報道」や話題の一覧の見出しから開きます。3社以上か AI 要約のある話題だけを検索エンジンに出します。
- **タグ**（`src/config/tags.ts`、`/tag/<slug>/`・`/tags/`）: AI・Apple・Google・任天堂・MLB・セキュリティ・半導体・EV・災害・政治・株価など、ジャンルをまたいだテーマ。見出しと AI 要約のキーワードで当てはめます。`/tag/ai/` は AI ニュースランキング。
- トップページ: 🔥いま話題・🚀急上昇・🔎注目ワード（と検索）・📰今日の重要ニュース・🤖AI ニュース・AI 要約（10秒）・📊メディア別・よく読まれている記事・新着・カテゴリ別。急上昇は `/rising/`、ランキングは `/ranking/`（24時間はスコアの順・1週間は報道の数の順・今日の重要ニュース）。
- **検索**（`/search/`）: 見出し・AI 要約とそのキーワード・抜粋・掲載元から探します。全角・半角、大文字・小文字、カタカナ・ひらがなの違いを吸収し、スペースで区切るとすべての言葉を含む記事に絞ります（カテゴリ・期間・並び順・AI 要約ありでも絞り込める）。一致した部分を強調し、直近の見出しによく出る言葉を検索の候補として表示します（`src/lib/search-core.ts`）。
- 記事は直近30日・最大12000件を保存します。更新の多いサイトの記事で上限が埋まっても、更新の少ないサイトの記事は各20件まで残します（古い話題は日別まとめに残ります）。
- 一覧ページ（新着・カテゴリ別・掲載元別）は25ページ（1000件）まで、検索は新しい6000件までを対象にします（収集元が多くてもビルド・公開と検索ページが重くならないように。`src/config/site.ts` の `maxListPages` / `searchLimit`）。
- トップページの「新着」とカテゴリ別の欄は、同じ掲載元の記事が続きすぎないよう、1つの掲載元から数件までにして新着順に並べます。

### 収集時の通信について

- 通常の閲覧者と同じに見えるよう、Windows 版 Chrome と同じヘッダー（User-Agent・Accept・`sec-ch-ua`・`Sec-Fetch-*` など）を同じ順序で送ります。
  Node の `fetch` は独自のヘッダーを付け足してしまうため、`node:https` で直接リクエストしています（`scripts/lib/http.ts`）。
- User-Agent の Chrome のバージョンは日付から自動で計算する（現行の 1 つ前の版）ので、放置しても古くなりません。
- 同じ運営元のサイト（`pc.watch.impress.co.jp` と `car.watch.impress.co.jp` のようにサブドメインだけが違うものを含む）へは 1 件ずつ、1.5〜4 秒のランダムな間隔を空けてアクセスし、サイトの巡回順も毎回入れ替えます。自動更新の開始時刻も毎回少しずらします。
- ブラウザが再読み込みのときにするのと同じく、前回の `ETag`・`Last-Modified` を送る条件付きリクエストにしています。フィードが変わっていなければ（304）本文を受け取らないので、相手サイトの負担と通信量が減ります（念のため12時間に1回は全部取り直します）。
- gzip / deflate / brotli / zstd の圧縮、リダイレクト、Shift_JIS・EUC-JP のフィードに対応しています。一時的なエラー（通信失敗・403・406・408・429・5xx）は 1 回だけ再試行し、`Retry-After` の指定（最大60秒）があれば従います。
- 収集元ごとの取得の状態（最後に取得できた日時、連続で失敗した回数と最後のエラー、ETag など）を `data/feeds.json` に記録し、管理画面の「収集元の状況」で確認できます。毎回の結果は Actions の実行ページの Summary にも表で出ます。

| しくみ | 内容 |
| --- | --- |
| 日別アーカイブ | `/daily/YYYY-MM-DD/` に「その日の話題のニュース」を毎日自動生成（`data/daily/` に永続保存）。日付ごとの恒久ページが増え続け、長い検索語でも拾われやすくなる |

| RSS / WebSub | 全体・カテゴリ別・日別まとめ・AI要約（`/summaries/rss.xml`）の RSS を配信し、更新のたびに WebSub ハブへ通知（Feedly などへすぐ届く） |
| SNS 自動投稿 | 公式アカウント **Bluesky [@topiatsume.bsky.social](https://bsky.app/profile/topiatsume.bsky.social)** に、毎時の公開のあと自動で投稿（Secrets の `BLUESKY_APP_PASSWORD` を登録すると動く。Mastodon・Misskey も Secrets を登録すれば同じ内容を投稿）。決まった時間の投稿: 朝（7〜10時台）「今日の重要ニュース」・昼（12〜14時台）「AI ニュース」・夜（21時以降）「今日の話題ニュース」・日曜の夕方（18〜20時台）「今週の話題ニュース TOP5」。話題が出たときの投稿: 「急上昇」（3時間で2社以上・計3社以上）・「いま話題」（4社以上・話題度50以上）・「10秒でわかるニュース」（AI 要約の1文目）。リンクは話題のページ・ランキングなど**サイトのページ**で、流入元が分かる印（`utm_source=bluesky`）付き。Bluesky ではリンクを短く表示し、ハッシュタグ（`#ニュース` とタグごとの `#AI`・`#MLB` など）とリンクカード（サイトの画像）を付ける。スパム対策: 深夜（0〜7時）は投稿しない・1日12件まで・急上昇などは1時間に1件まで（種類ごとに1日の上限）・同じ話題は二度投稿しない・フォローやいいね・返信の自動化はしない（`scripts/lib/social.ts`）。管理画面の「今すぐ Bluesky に投稿」で、待たずに最新の話題を投稿することもできる（下の「管理画面から今すぐ投稿する」） |
| シェアボタン | 要約ページ・日別まとめ・ランキングに X・LINE・はてブ・Bluesky・Facebook のシェアボタン（各サービスの共有ページへのリンクだけで、API は使わない） |
| 再訪のしかけ | 「あとで読む」（記事をブラウザに保存、`/saved/`）、前回の訪問のあとに届いた記事に印を付ける、AI 要約の RSS。どれもブラウザ内だけで動き、サーバーには何も送らない |
| ホーム画面に追加 | Web アプリマニフェスト（PWA）とアイコン、サービスワーカー（オフラインのとき前に見たページを表示、`/_astro/` のファイルを使い回す）、2回目以降の訪問で「ホーム画面に追加」を小さく案内（`src/scripts/pwa.ts`） |

デプロイ後の通知と投稿は `scripts/notify.ts`（ワークフローの `notify` ジョブ）が行います。
`SITE_BASE_URL=<公開URL> NOTIFY_DRY_RUN=1 npm run notify` で、送信せずに内容だけ確認できます（`NOTIFY_SKIP_PING=1` を付けると検索エンジン・フィードへの通知を省き、SNS の投稿だけを行います）。
投稿した記録は `data/social.json` に残り（同じ話題を二度投稿しないため）、管理画面の「概要」で見られます。

#### 管理画面から今すぐ投稿する

管理画面の「概要」の「SNS（Bluesky）の自動投稿」にある **「今すぐ Bluesky に投稿」** を押すと、次の毎時の更新を待たずに投稿します。

1. 管理画面が投稿の依頼（`data/social-request.json`。依頼ごとの ID と日時）を GitHub に保存する。この保存でサイトの更新（`update.yml`）が始まる
2. 最新の記事を取り込んでサイトを公開したあと、`scripts/notify.ts` が依頼を見つけて投稿する（リンク先のページが必ずあるよう、公開してから投稿する。押してから2〜4分）
3. 結果を `data/social.json` の `manual` に書き、管理画面がそれを読んで「投稿しました」と投稿へのリンク（Bluesky で見る・サイトのページ）を表示する

- 投稿するのは、まだ投稿していない話題のうち 急上昇 → いま話題 → 10秒でわかるニュース の順に1件。どれもなければ「いま話題のニュース」のまとめ（話題度の高い順に5件。同じ時間帯は1回まで）。その時間帯の決まった投稿（朝・昼・夜・日曜）がまだなら、それも一緒に投稿する
- 深夜や前の投稿の直後でも投稿する（運営者が押したときだけ）。同じ話題は二度投稿しない。24時間に24件まで（自動投稿と合わせて。誤って何度も押したときの歯止め）
- 30分以上たっても処理されなかった依頼は投稿しない（更新の失敗などで、思わぬ時間に投稿しないように）
- Secrets に `BLUESKY_APP_PASSWORD` がなければ、そのことと登録ページへのリンクを表示する。ページを開き直しても、処理中の依頼があれば結果を待って表示する

### 運営者が行う必要があること

1. **Google Search Console に登録する（Google 検索に早く載せるために最重要）**
   1. https://search.google.com/search-console で「URL プレフィックス」に公開URLを入力
   2. 確認方法「HTML タグ」を選び、表示された `content="..."` の値をコピー
   3. GitHub の Settings → Secrets and variables → Actions → **Variables** に `PUBLIC_GOOGLE_SITE_VERIFICATION` として登録し、Actions から再実行
   4. Search Console で「確認」→「サイトマップ」に `sitemap.xml` を送信（`sitemap-index.xml` でも同じ）
2. **Bing Web マスターツール**（任意）: Search Console から設定をインポートするか、`PUBLIC_BING_SITE_VERIFICATION` を登録
3. **SNS（Bluesky）の自動投稿を動かす**: GitHub の Settings → Secrets and variables → Actions → **Secrets** に `BLUESKY_APP_PASSWORD`（Bluesky の「設定 → プライバシーとセキュリティ → アプリパスワード」で発行したもの）を登録すると、次の毎時の更新から投稿が始まります。
   - アカウント（`@topiatsume.bsky.social`）は既定で入っているので、ハンドルの登録は不要です（別のアカウントで投稿するときだけ `BLUESKY_IDENTIFIER` を登録）。
   - プロフィール（名前・説明・アイコン・バナー・サイトの URL）と「自動で投稿するアカウント」（bot）のラベル、固定の紹介の投稿は設定済みです。
   - サイトのフッター・サイドバー・トップ・急上昇・話題のページに「Bluesky でフォロー」の案内が出ます（`src/config/site.ts` の `socialAccounts`。構造化データの `sameAs` にも入る）。
   - X は使いません（API に無料枠がなく、URL つきの投稿は1件0.2ドルのため）。管理画面の「概要」の下書きから、Bluesky の投稿画面を開いて手で追加の投稿もできます。

| Secret | 内容 |
| --- | --- |
| `BLUESKY_APP_PASSWORD` | Bluesky のアプリパスワード（必須。アカウントのパスワードではなく、アプリパスワードを使う） |
| `BLUESKY_IDENTIFIER` | 投稿するアカウントのハンドル（任意。既定は `topiatsume.bsky.social`） |
| `MASTODON_URL` / `MASTODON_TOKEN` | （任意）インスタンスのURL（例: `https://mastodon.social`）と、`write:statuses` 権限のアクセストークン |
| `MISSKEY_URL` / `MISSKEY_TOKEN` | （任意）インスタンスのURL（例: `https://misskey.io`）と、「ノートを作成・削除する」権限のアクセストークン |

※ 検索結果に表示されるまでには通常数日〜数週間かかり、順位は保証されません。見出しを集めただけのページは評価されにくいため、独自ドメインの取得や独自コンテンツの追加が効果的です。

## AI要約（管理画面）

要約の JSON は運営者が作ります。管理画面でプロンプトを作ってコピーし、自分でチャット AI（ChatGPT・Gemini など）に貼り付け、返ってきた JSON を管理画面に貼り付けて保存します。
サイト側から有料の AI API を呼ぶ仕組みはありません（費用はかかりません）。

記事ごとに AI の要約を載せられます。要約のある記事は一覧に要約が表示され、タイトルから当サイトの要約ページ（`/summary/<記事ID>/`）に移動します。
要約ページは元記事が古くなって一覧から消えても残り、検索エンジンにも送信されます。

### 使い方（`/admin/summaries/`）

管理画面の「AI要約・記事」（https://topiatsume.pages.dev/admin/summaries/ ）を開きます。

1. **記事を選ぶ** — 件数（10 / 20 / 30 / 50件）・カテゴリ・並び順（話題の順＝報じたサイトが多い順 / 新しい順）を選ぶと、要約のない記事が上から選ばれます。チェックで個別に外せます。利用規約で要約を禁じている掲載元（`summary: false`）の記事は候補に出ません
2. **プロンプトをコピー** — 「プロンプトをコピー」で丸ごとコピーし、ChatGPT や Gemini など Web ページを読めるチャット AI にそのまま貼り付けます。要約の長さ・要点（箇条書き）の有無も選べます
   - チャット AI に一度に貼り付けられる長さには上限があるので、「1回に貼り付ける長さの上限」（既定15,000字。8,000〜60,000字・上限なし）を超えるプロンプトは何回かに分けます（「1回目」「2回目」…のボタンで切り替え、1回ずつ AI に渡して、回答をそれぞれ確認・保存します）
   - 「ファイルで保存」で今の回をテキストファイルに、「全部を1つのファイルで保存」で分けない全体を保存できます。AI の画面でファイルを添付し、表示される一言（「添付したファイルは記事の要約の依頼です…」）を送れば、貼り付けの上限を気にせずに依頼できます
   - 「AI の回答のしかた」を「JSON ファイル」にすると、AI に `summaries.json` を作ってもらうよう頼みます（ファイルを作れない AI はコードブロックで答えます）
3. **AI の回答を貼り付けて確認** — AI は ```` ```json ```` のコードブロック1つで回答するよう指示してあるので、そのブロックをコピーして貼り付け、「内容を確認する」。一覧にない id、短すぎ・長すぎる要約、「アクセスできませんでした」のような断り文ははじかれます。保存したくない要約はチェックを外せます
   - 「ファイルから読み込む」で、AI が作った `summaries.json`・回答を保存したファイル・「保存用JSON」を読み込めます（複数のファイルを一度に選べ、回答の欄へのドラッグでも読み込めます）。読み込むとそのまま内容を確認します
4. **保存して公開** — GitHub に1つのコミットとして保存し、1〜3分ほどでサイトに反映されます

**要約が保存された記事は「要約する記事を選ぶ」に出ません**（サイトの更新後は要約のない記事だけが並び、保存した直後もサイトに反映されるまでの間は管理画面が自動で外します）。
AI が読めなかった記事（`unavailable`）や回答に含まれなかった記事は要約待ちに残るので、次のプロンプトで改めて依頼できます（AI が開けなかった記事の扱いは下の「AI が記事を開けないとき」）。

#### AI に渡すプロンプトの中身

AI の回答をプログラムがそのまま読み込めるよう、プロンプトには次のことを細かく書いています（`src/lib/summary-core.ts` の `buildSummaryPrompt`）。

- 作業の手順（url を開いて本文を読む → 要約 → 読めない記事は `unavailable` → 全件を1つの JSON 配列にまとめる）
- 要約の書き方（字数、常体、最初の文で「誰が・何を・どうした」、要点は3つまで・1つ40字以内で具体的な事実、本文の言い回しを10字以上続けて写さない・直接の引用をしない、数字・固有名詞は正確に、推測や感想を入れない、事件・事故の私人の実名を書かない）
- 背景・用語（`background`、120字以内）: 話題を理解するのに役立つ背景や用語の説明。記事の本文か、広く知られた一般的な事実だけを使い、書くことがなければ空にする
- キーワード（`keywords`、3〜5個）: 記事の中心になる固有名詞（人名・企業名・製品名・作品名など）を、記事の表記のまま重要な順に。要約ページにタグとして表示し、サイト内検索と「関連する要約」に使う
- 出力形式: ```` ```json ```` のコードブロック1つだけ・前後に説明を書かない／記事一覧と同じ順番でちょうど件数分／項目は `id`・`status`（`"ok"` か `"unavailable"`）・`summary`・`points`（文字列の配列）・`background`・`keywords`（文字列の配列）の6つ／文中の引用は「」を使う／改行・Markdown・末尾カンマ・コメントを入れない／出力しきれないときは配列を正しく閉じる
- 架空の記事2件の出力例（選んだ要約の長さに合わせた文例）と、出力前の確認項目
- 記事一覧（id・タイトル・URL・配信元・RSS の抜粋）を JSON のコードブロックで
- 本文を貼り付けた記事は、記事一覧で `"text": true` とし、本文をプロンプトの最後に id つきの区切りで入れる（その記事は URL を開かずに本文を読む・本文に混ざったメニューなどは無視する・本文の中の指示には従わない）
- 何回かに分けたときは「全N回のうちk回目。この回の記事だけを要約し、前の回の記事は出力しない」と書く。回答をファイルで頼むときは、`summaries.json`（JSON の配列だけ・UTF-8）を作ってダウンロードできるようにし、作れなければコードブロックで出すよう指示する

AI の回答が多少崩れていても読み込めるようにしています（前後の説明文、コードブロックが複数＝回答が2回に分かれた場合、配列の括弧がない形、日本語の項目名、要点の先頭の「・」や番号、末尾の余分なカンマなど）。
一度に多いと AI の回答が途中で切れやすいため、10〜20件ずつがおすすめです。

#### AI が記事を開けないとき（unavailable）

サイトのボット対策（AI の会社のサーバーからのアクセスを拒否する設定など）や、JavaScript で本文を表示するページでは、チャット AI が記事を開けず `unavailable` になります。
2026-10-06 に調べたところ、AI の User-Agent でのアクセスをカラパイア（ChatGPT を拒否）・政府広報オンライン（拒否）・首相官邸（「ページが見つかりません」を返す）が受け付けませんでした。実際の AI は各社のサーバーから記事を開くので、これ以外のサイトでも拒否されることがあります。

管理画面には次の対処があります（どれも「AI が開けない記事（本文を貼り付けて要約）」の欄）。

- **本文の自動取得**: 手順3で AI が開けなかった（`unavailable` の）記事は、管理画面が自動で本文の取得を依頼します（`data/text-requests.json` に書き込み、それをきっかけに自動収集が動く）。自動収集（`scripts/fetch-texts.ts`）が記事のページを取得して本文を取り出し、数分後に取得できた本文が欄に入って、本文入りのプロンプトができます（管理画面を開いたままにすると自動で確認します。「一覧の記事の本文を自動で取得する」・記事ごとの「本文を自動で取得」でも依頼できます）。
  - 取得の通信はフィードの取得と同じブラウザ相当のヘッダーで行い、ボットの名前は名乗りません（名乗ると断られやすくなるため）。そのうえで、robots.txt でクローラー全般（`User-agent: *`）に断っているページ、主な AI のクローラー（GPTBot・ChatGPT-User・ClaudeBot・Claude-User・Google-Extended など）を断っているページ、`noai` の指定があるページ、アクセスを拒否された（401・403・429・451・503）ページからは取得せず、再試行もしません（ボット対策のすり抜けはしません）。1回の実行で15件まで、同じサイトへは間隔を空けて1件ずつ取得します。取得の方針は運営者情報のページ（`/about/#fetch`）にも載せています。
  - 取得した本文はリポジトリやサイトにそのまま置かず、運営者の公開鍵で暗号化して `data/texts.json` に置きます。復号に使う秘密鍵は、ログインの初回設定のときに作り、トークンと一緒にパスワードで暗号化してブラウザにだけ保存します（公開鍵は管理画面が `data/text-keys.json` に登録します）。
  - 取得できなかった記事には理由（サイトが断っている・拒否された・本文がない（動画だけのページなど）など）を出します。その場合は下の方法で本文を貼り付けてください。

- **本文を貼り付けて要約する**: 自分のブラウザで記事を開いて本文をコピーし、管理画面に貼り付けると、欄のいちばん下に**本文入りのプロンプト**が自動でできます。それをコピー（またはファイルで保存して添付）して AI に渡すと、AI は URL を開かずに本文から要約の JSON を書きます。回答は手順3で確認・保存します（手順1・2の URL を開いてもらうプロンプトとは別に作るので、二重に依頼することはありません）。
  - 「本文をコピー（トピあつめ）」ボタンをブックマークバーにドラッグして登録しておくと、記事のページで押すだけで本文（メニュー・関連記事・コメント・共有ボタンなどを除いたもの）をコピーできます。うまく取れないときは、本文を選んでから押すか、本文を選んでコピーします。コピーと一緒に出る「ファイルで保存」で、本文をテキストファイルに保存することもできます。
  - コピーした本文は「本文をまとめて貼り付け」の欄に貼れば、ページの URL で記事に自動で振り分けます（いくつ続けて貼ってもかまいません）。保存した本文のファイルは「本文のファイルを読み込む」でまとめて読み込めます。記事ごとの欄に直接貼り付けることもできます。
  - 別のサイトのページを貼った・本文が短い・長すぎる（1記事6,000字まで使う）ときは注意を出します。本文入りのプロンプトも「1回に貼り付ける長さの上限」に合わせて何回かに分け、ファイルで保存できます。
  - 貼り付けた本文はプロンプトを作るのに使うだけで、サイトや GitHub には保存・公開しません（そのタブの中だけに残り、閉じると消えます）。
- **同じ話題の別の記事に切り替える**: 同じ出来事をほかのサイトも報じていれば、「代わりに ○○ の記事を選ぶ」でその記事に切り替えられます。同じ話題がすでに要約済みなら、そのことを表示します。

AI が開けなかった記事はこのブラウザに14日間記録され、手順1で自動では選ばれません（本文を貼った記事も、本文入りのプロンプトで依頼するので手順1では選ばれません）。開けなかった記事が2件以上あるサイトも「AI が開けないことが多いサイト」として自動では選ばれなくなります（そのサイトの記事を本文なしで要約できると解除されます。「記録を消す」でも消せます）。

※ 本文の自動取得は、サイトが断っていない範囲でだけ行います。ブラウザのふりをしてボット対策をすり抜けたり、拒否されたのに取り直したりはしません（サイトの意向に反し、利用規約や著作権の問題になりやすいため）。取得した本文も、貼り付けた本文も、要約を作るためにだけ使い、公開しません。利用規約で要約を禁じているサイト（`summary: false`）の記事は、もともと要約の候補に出ません。

#### 要約の修正・作り直し・削除

- **修正**: 「保存済みの要約」で記事を探し（タイトル・要約で絞り込み可）、「編集」で要約・要点・背景・キーワードを直して「保存して反映」。最初に保存した日時と記事の情報はそのままで、手直しした日時（`updatedAt`）を記録します
- **AI で作り直す**: 手順1で「要約済みの記事も選べるようにする」にチェックすると、要約済みの記事が先頭に並びます（自動では選ばれません）。作り直したい記事にチェックを入れてプロンプトを作り、回答を保存すると上書きされます
- **削除**: 「保存済みの要約」で選んで削除すると、その記事は要約待ちに戻ります
- 管理画面で扱えるのは新しい300件までです。それより古い要約は GitHub 上で `data/summaries/YYYY-MM.json` を直接編集してください

### 記事の非表示（NGワード・サイト・個別）

管理画面の「記事の非表示」で、見出しに含まれると非表示にする **NGワード** と、記事を載せない **サイト**（サブドメインを含む）を設定できます。
手順1の一覧でチェックした記事を「選んだ記事をサイトから非表示」で個別に外すこともできます。

設定は `data/blocklist.json` に保存され、一覧・ランキング・検索・RSS・日別まとめ・要約ページ・SNS 投稿のすべてから外れます。
収集したデータからは消さないので、設定を消せば元に戻ります（個別に外した記事は「非表示中の記事」から再表示）。
AdSense などの広告は、成人向け・暴力的・ショッキングな内容のページへの掲載が禁止されています。収益化する前に、気になる記事は非表示にしておくと安心です。

### ログイン（最初に1回だけ: トークンとパスワードの設定）

管理画面は静的なページなので、保存には GitHub のアクセストークンを使います。`/admin/` を開くとログインページ（`/admin/login/`）に移ります。

1. https://github.com/settings/personal-access-tokens/new で **Fine-grained** トークンを作成
2. Repository access で **このリポジトリだけ** を選択
3. Repository permissions の **Contents** と **Actions** を **Read and write** にする（有効期限も設定推奨）
4. ログインページの「管理画面の初回設定」にトークンと、管理画面を開くためのパスワード（10文字以上）を入力して「確認して設定」

2回目からはパスワードだけでログインできます。しくみと安全対策:

- トークンが本当にこのリポジトリに書き込めるかを GitHub で確かめてから、パスワードで暗号化（PBKDF2-SHA256 60万回で鍵を作り AES-GCM で暗号化）して、そのブラウザにだけ保存します。パスワード自体はどこにも保存しません。トークンは GitHub API 以外には送りません。
- ログイン中の状態はタブを閉じると消えます。30分操作がないか、ログインから8時間たつと自動でログアウトします（選んだ記事と貼り付けた回答は、同じタブで再ログインすると戻ります）。
- パスワードを5回続けて間違えると30秒ログインできなくなり、さらに間違えるたびに待ち時間が延びます（最長15分）。
- 管理画面は自分のサイトのファイルと GitHub API にしか接続できないよう制限し（Content Security Policy）、ほかのサイトの枠（iframe）の中では表示しません。検索エンジンには `noindex` と robots.txt で登録されないようにしています。
- **パスワードを忘れたとき**: パスワードはどこにも保存していない（運営者のブラウザの中でトークンの暗号化に使うだけ）ため、誰にも調べたり設定し直したりできません。ログインページの「パスワードを忘れた・トークンを入れ直したいとき」→「保存したトークンを消してやり直す」を押し、初回設定でトークンと新しいパスワードを入れ直します。トークンの値が手元にないときは、GitHub の Settings → Developer settings → Personal access tokens → Fine-grained tokens で、そのトークンの「Regenerate token」を押すと、同じ権限のまま新しい値を発行できます。本文を読むための鍵も作り直されるので、それより前に自動で取得した本文は読めなくなります（必要なら依頼し直します）
- トークンを作り直したときも、同じ手順で設定し直します。
- 以前の版で「このブラウザに記憶する」を選んで保存したトークンは、初回設定の欄に入るので、パスワードを決めれば暗号化して保存し直します（暗号化していないトークンはそのとき消えます）。
- 共用のパソコンでは使わないでください。

### コマンドラインでも使えます

```sh
npm run summaries -- prompt --count 20 --sort popular --out prompt.txt   # プロンプトを作る（--category tech など）
npm run summaries -- import 回答.json                                     # 回答を検証して data/summaries/ に保存
```

要約は `data/summaries/YYYY-MM.json`（記事の公開月ごと、1記事1行）に保存されます。

## アクセス解析（訪問者数・いま見ている人数・よく読まれている記事）

記録の受け取りと集計は Cloudflare の無料プランで行います。サイトと同じドメインの `/api`（Cloudflare Pages の Functions。`functions/api/[[path]].ts`）が、Worker「topiatsume-analytics」（`analytics/`）の Durable Object（SQLite）に記録を渡して数えます。Worker 自体は外から直接は呼べません（`workers.dev` で公開しない）。

- **管理画面の「アクセス解析」**（`/admin/analytics/`。管理画面の上の「アクセス解析」から）
  - リアルタイム（15秒ごとに更新）: いま見ている人数、直近30分の1分ごとの閲覧数、いま見られているページ、最近の動き（閲覧・記事を開いた・検索・保存）、この週（月曜から）・この月の訪問者数（WAU・MAU）
  - 期間（今日・昨日・7日間・30日間・90日間）ごと: 訪問者数・閲覧数・サイトに来た回数・記事を開いた回数・記事を開いた人の割合・1ページの閲覧時間・1ページで離れた人の割合・前にも来た人の割合（前の期間との比較つき）、閲覧数と訪問者数の推移、よく読まれている記事・ページ、どこから来たか（検索エンジン・SNS・AI チャット・ほかのサイト・直接）と来たサイト、入口のページ、サイト内で検索された言葉（0件だった回数つき）、カテゴリ、よく開かれた掲載元、時間帯、1人が見たページ数、「あとで読む」に保存された記事、端末・OS・ブラウザ、国・地域
- **サイト**: 「よく読まれている記事」のページ（`/popular/`、24時間・1週間）、トップとサイドバーの「よく読まれている記事」、上位10件の記事の「人気N位」の印、ヘッダーの「人気」、トップと人気のページの「いまN人が閲覧中」（2人以上のとき）。人気の記事は自動更新のたびにサーバーから `data/popular.json` に取り込みます（`scripts/popular.ts`）。
- **要約の候補**: 管理画面の手順1の並び順で「よく読まれている順」（直近7日に読まれた人数）を選べます。よく読まれているのに要約のない記事から要約すると効果的です。

数え方とプライバシー:

- Cookie は使いません。IP アドレスは保存せず、IP アドレスとブラウザの種類と「日ごとに変わる塩」から作った匿名の番号で人数を数えます（塩は翌日に捨てるので、日をまたいで同じ人かは分かりません）。複数の日の訪問者数は日ごとの人数の合計です。
- 週・月の訪問者数（WAU・MAU）は、ブラウザに残っている前回の閲覧日時から「この週・この月に初めての訪問か」だけを送ってもらい、それを足して数えます（日をまたいで同じ人を追いかけません。サイトのデータを消したブラウザ・別の端末は別の人に数えます）。
- 「記事を開いた」は記事の見出し・「元記事」のリンクを押した回数、「サイトに来た」は前の閲覧から30分以上空いて来た回数です（「あとで読む」の新着の印と同じ訪問の記録を使います）。人気の記事は、記事を開いた・要約ページを読んだ・保存した人の数（同じ人は1回）で並べます。
- 検索エンジンなどのボット、「Do Not Track」「Global Privacy Control」を有効にしたブラウザ、自動操作のブラウザ、管理画面にログインしたブラウザ（自分の閲覧で数字が増えないよう自動で除外。アクセス解析のページで戻せます）は数えません。
- 個々の記録は14日、日ごとの集計は約400日残します。送る情報・送り先・目的はプライバシーポリシー（`/privacy/#analytics`）に載せています。

アクセス解析は、サイトを Cloudflare に公開していれば（下の「公開先（Cloudflare）」）自動で動きます。`analytics/` を変更して push すると、`.github/workflows/analytics.yml` が Worker を公開し直します。

- **無料の範囲**: Cloudflare の無料プランは1日にリクエスト10万回・書き込み10万行などが上限です。ページを見るごとに1回と、表示している間は2分ごとに1回（いま見ている人数のため）、離れるときに1回送るので、1ページあたり2〜3回、月100万PV（1日約3万3千PV）くらいまでが無料の範囲です。それを超えるときは Workers の有料プラン（月5ドル）にします。記録する件数は1日4万件までにしてあり（`analytics/wrangler.jsonc` の `MAX_EVENTS_PER_DAY`）、上限を超えてもその日の残りの記録が止まるだけで、サイトの表示には影響しません。
- `/api` は、サイトと同じドメインのページからの記録だけを受け取ります（同じドメインなので CORS も不要）。管理画面からの問い合わせには、ログイン中の GitHub のトークンでサイトのリポジトリに書き込めるかを GitHub に確かめてから答えます（トークンは保存しません）。
- 手元で試すとき: `cd analytics && npm install && npx wrangler dev` で解析の Worker を起動し、別の端末でサイトを `PUBLIC_ANALYTICS_URL=/api npm run build` でビルドしてから、ルートで `analytics/node_modules/.bin/wrangler pages dev` を動かすと、本番と同じ組み合わせ（`dist` ＋ `/api` ＋ Durable Object）を http://localhost:8788 で試せます。Worker だけを試すときは `PUBLIC_ANALYTICS_URL=http://127.0.0.1:8787`（入口の中身は `analytics/src/front.ts`、集計の中身は `npm test` の `tests/analytics*.test.ts` で確かめています）。

## フォロー・通知（読者向け）

読者がこのブラウザだけで使える機能です（設定はブラウザのローカルストレージに保存し、通知をオンにしたとき以外はサーバーに送りません）。

- **フォロー**: ジャンル・掲載元・キーワードをフォローすると、新着を「フォロー中」（`/following/`）にまとめます。ジャンル・掲載元のページの「フォローする」、検索結果の「フォローする」、サイドバーのジャンル、記事の右下の「…」のメニューから追加できます。ヘッダーのベルに、前に「フォロー中」を見たあとの新着の数を出します。キーワードは見出しに含まれていれば当てはまり（全角・半角、カタカナ・ひらがなの違いは吸収。英数字だけの言葉は単語として当てはまるときだけ）、スペースで区切るとすべてを含むものだけになります（共通の処理は `src/lib/follow-core.ts`）。
- **通知（プッシュ通知）**: 「フォロー中」のページでオンにすると、フォローに当てはまる新着（毎時のサイトの更新のあと。1件なら見出し、複数なら件数と見出し3件）、いま話題のニュース（4社以上が報じた出来事。同じ話題は1回だけ）、運営からのお知らせを、サイトを開いていないときもブラウザの通知で知らせます。「1日1回、朝7時ごろにまとめて」「夜（23時〜7時）は送らず朝にまとめる」も選べます。iPhone・iPad はホーム画面に追加したときだけ使えます（iOS 16.4 以降）。
- **表示しない（ミュート）**: 掲載元・キーワード・ジャンルの記事を一覧から隠します（ジャンル・掲載元のページでは、そのジャンル・掲載元は隠しません）。隠した件数は一覧の上に出て、一時的に表示もできます。
- **既読**: 開いた記事の見出しの色を変えます（「表示の設定」で、一覧から隠す・何もしないも選べる）。
- **表示の設定**（`/settings/`）: 文字の大きさ・抜粋の表示・読んだ記事・画面の色、表示しない設定、設定の書き出し・読み込み（ほかの端末に移す）、アクセス解析で数えない設定、設定の消去。
- そのほか、ページの先頭に戻るボタン、運営からのお知らせ（サイトの上部。閉じると、内容が変わるまで出ない）、トップページの「編集部のピックアップ」。

通知の仕組み（費用はかかりません。アクセス解析と同じ Cloudflare の無料プラン）:

- サイトのビルドで `updates.json`（直近36時間の新着最大1200件と、3社以上が報じた話題。`src/pages/updates.json.ts`）を作ります。「フォロー中」のページとヘッダーの数はこれを読みます。
- 公開のワークフローが Cloudflare に公開したあと `POST /api/push/check` を呼ぶと、Pages の Functions が**公開したサイトの** `updates.json` を読んで（呼んだ側の内容は使わない）Durable Object に渡し、はじめて見た記事を購読ごとのフォローと照らし合わせて送ります（`analytics/src/push.ts`）。最初の1回は記録だけして送りません。購読は40件ずつ処理し、残りは1秒後のアラームで続けます（無料プランの1回の処理で外へ送れる数の上限のため）。
- 通知の内容は RFC 8291（aes128gcm）で暗号化し、VAPID（RFC 8292）で送り主を証明します（`analytics/src/webpush.ts`。RFC の例と同じ結果になることをテストで確かめています）。VAPID の鍵は Durable Object が最初に作って保存するので、秘密の値を設定する必要はありません。送り先は通知を届ける会社（Google・Mozilla・Apple・Microsoft）の URL だけに限ります。
- ブラウザ側はサービスワーカー（`public/sw.js`）が通知を表示し、押すとサイト内のページを開きます（ほかのサイトの URL は開かない）。購読の登録・変更は `src/scripts/push-client.ts`。
- 保存するのは、購読（通知を届ける URL と鍵）・フォロー・表示しない設定・受け取り方だけで、IP アドレスやアクセス解析の記録とは結び付けません。届かなくなった購読（取り消し・期限切れ）は自動で消します。購読は2万件まで（`analytics/wrangler.jsonc` の `MAX_PUSH_SUBSCRIBERS`）。プライバシーポリシーの `/privacy/#push` に載せています。

## 公開・自動更新

`.github/workflows/update.yml` が以下のタイミングで「テスト → 収集 → 本文の自動取得（管理画面からの依頼があるときだけ） → よく読まれている記事の取得 → データをコミット → ビルド → Cloudflare Pages へ公開 → フォロー中の新着の通知 → 検索エンジン・SNS へ通知」を行います。
データのコミットは、再実行や同時実行で古いコミットから始まった場合でも、ブランチの最新状態に取り込み直してから push します。

- **自動更新タイマー**（`.github/workflows/timer.yml`）による約1時間ごとの実行
- 既定ブランチへの push（管理画面から要約を保存したときも）
- 管理画面の「今すぐ更新」ボタン、または Actions タブからの手動実行（Run workflow）

### 公開先（Cloudflare）

リポジトリの Secrets に `CLOUDFLARE_API_TOKEN` と `CLOUDFLARE_ACCOUNT_ID` があると、`update.yml` は次のように公開します。

1. Cloudflare Pages のプロジェクト `topiatsume`（ルートの `wrangler.jsonc`）がなければ作り、公開先の URL（`https://topiatsume.pages.dev`）を調べる。アクセス解析の Worker（`analytics/`）がまだなければ先に公開する
2. その URL 用にサイトをビルドし（`BASE_PATH=/`、アクセス解析は `/api`）、`wrangler pages deploy` で `dist`（静的なページ）と `functions/`（`/api`）を公開する
3. フォロー中の新着の通知を確認する（`POST /api/push/check`。上の「フォロー・通知（読者向け）」）
4. 以前の公開先の GitHub Pages には、新しい URL の同じページへ移る転送ページ（`scripts/redirect-stub.mjs`）を公開する。サイトのページごとに、正規の URL（canonical）と即時の転送を入れたページを置くので、検索エンジンにも移転先が伝わりやすい（ないページは 404.html から移す）

Secrets がないときは、これまでどおり GitHub Pages にサイトを公開します（アクセス解析なし。GitHub Pages の設定（Settings → Pages → Source）は **GitHub Actions** のまま）。

設定のしかた:

1. Cloudflare のダッシュボードの「My Profile」→「API Tokens」→「Create Token」で、テンプレート「Edit Cloudflare Workers」からトークンを作る（Workers と Pages を編集できる権限）。ダッシュボードに出る「Account ID」も控える
2. GitHub の Settings → Secrets and variables → Actions → **Secrets** に `CLOUDFLARE_API_TOKEN`（トークン）と `CLOUDFLARE_ACCOUNT_ID`（Account ID）を登録する（トークンはチャットやリポジトリに書かない）
3. 管理画面の「今すぐ更新」（または Actions の Run workflow）で公開する

- 応答ヘッダーは `public/_headers`（管理画面は枠の中で表示させない・検索に出さない・保存させない、`/_astro/` は長く保存、通知のサービスワーカー `sw.js` は毎回確かめる）、以前の URL（`/matmsait/...`）の転送は `public/_redirects` で指定しています。
- 管理画面のログイン（暗号化したトークンと本文を読むための鍵）は URL ごとにブラウザに保存されるので、新しい URL の管理画面では最初に1回、初回設定（トークンとパスワード）が必要です。
- Cloudflare Pages の無料プランでは、静的なページの配信は無料・無制限、`/api`（Functions）は Workers の無料枠（1日10万回）に含まれます。

### 自動更新タイマー

GitHub の定期実行（`schedule`）は「ベストエフォート」で、作ったばかりのリポジトリでは登録されずに動かないことがあります（このリポジトリでも一度も動きませんでした）。
そこで、定期的な更新は GitHub の定期実行に頼らず、次の仕組みで行っています。

1. 自動更新タイマー（`timer.yml`）が、前回の収集・公開（`update.yml`）から60分たつまで待つ
2. `update.yml` を実行し、自分自身（`timer.yml`）を次に予約する（1 に戻る）

- 待っている間に push や「今すぐ更新」で更新されたら、そこから数え直します（同じ時間帯に二重に更新しません）。
- タイマーは常に1つだけ動きます。何かの理由で止まっても、`update.yml` が動くたびに（push・「今すぐ更新」など）自動で再開します。管理画面の「サイトの更新」に「自動更新: 動作中／停止中」と次の更新の目安が出ます。
- 待っている間も GitHub Actions の実行時間を使います。**公開リポジトリでは無料**ですが、非公開リポジトリでは月の無料枠を超えてしまうため、非公開にするとタイマーは自動で止まります（その場合は下の外部 cron を使ってください）。
- 更新の間隔は、リポジトリの変数（Settings → Secrets and variables → Actions → Variables）`UPDATE_INTERVAL_MINUTES` で変えられます（15〜360分、既定60分）。
- 予備として、GitHub の定期実行が動くようになった場合は3時間ごとにタイマーの再開も試みます。

外部の cron サービス（[cron-job.org](https://cron-job.org/) など）から次の API を毎時呼んで更新することもできます（トークンは Actions: Read and write だけを付けた Fine-grained トークン）。
タイマーが動いていれば必要ありません。

```sh
curl -X POST -H "Authorization: Bearer <トークン>" -H "Accept: application/vnd.github+json" \
  https://api.github.com/repos/<owner>/<repo>/actions/workflows/update.yml/dispatches \
  -d '{"ref":"<既定ブランチ>"}'
```

### 独自ドメインを使う場合

Cloudflare のダッシュボードで Pages のプロジェクト `topiatsume` →「Custom domains」にドメインを追加し、GitHub のリポジトリの変数（Settings → Secrets and variables → Actions → Variables）`SITE_URL` にその URL（例: `https://example.com`）を設定すると、次の更新からそのドメイン用にビルドします（正規の URL・サイトマップ・RSS などがそのドメインになり、以前の GitHub Pages の転送先もそのドメインになります）。
AdSense の審査（`pages.dev` のような共用のドメインでは申し込めない）を考えると、収益化する段階では独自ドメインを強く推奨します。

### 収集元を追加する

`sources.yaml` に追記します。`category` は `site.ts` の `categories` にある slug を指定します。

```yaml
- id: example          # 英小文字・数字・ハイフン（URL に使われる）
  name: 例のサイト
  feedUrl: https://example.com/feed
  siteUrl: https://example.com/
  category: tech
  # 任意
  aggregator: true     # 他サイトの記事を紹介するフィードの場合（記事の掲載元として紹介先のサイトを表示）
  stripTitle: '^【PR】' # タイトルから取り除く部分（正規表現）
  limit: 10            # 1回の取得で取り込む件数の上限（1日に数百件を配信するサイトで一覧が埋まらないように。1〜50、既定50）
  excerpt: false       # 抜粋を載せず、見出しとリンクだけにする（利用条件で抜粋の掲載がはっきりしないサイト）
  summary: false       # AI 要約の候補にしない（利用規約で記事の要約の掲載を禁じているサイト）
```

追記したら `npm test`（設定ミスの検出）と `npm run fetch`（実際に取得できるか）で確認してください。
登録する前に、そのサイトの利用規約で商用サイトからの RSS・見出しの利用が禁じられていないかを確認し、結果を [`docs/SOURCES.md`](docs/SOURCES.md) に記録してください（登録を見送ったサイトも、理由と一緒に残します）。

## 広告・アクセス解析の有効化

GitHub の **Settings → Secrets and variables → Actions → Variables** に登録すると、次回のデプロイから反映されます（`.env.example` 参照）。

| 変数 | 内容 |
| --- | --- |
| `PUBLIC_ADSENSE_CLIENT` | AdSense のパブリッシャー ID（例: `ca-pub-1234567890123456`）。全ページに AdSense タグを出力（自動広告）し、`ads.txt` も生成 |
| `PUBLIC_ADSENSE_SLOT` | （任意）広告ユニットのスロット ID。記事一覧の 10 件ごととサイドバーに広告枠を表示 |
| `PUBLIC_GA_ID` | （任意）Google アナリティクス 4 の測定 ID（例: `G-XXXXXXXXXX`） |
| `PUBLIC_GOOGLE_SITE_VERIFICATION` | （任意）Google Search Console の所有権確認コード |
| `PUBLIC_BING_SITE_VERIFICATION` | （任意）Bing Web マスターツールの所有権確認コード |
| `PUBLIC_ANALYTICS_URL` | （任意）アクセス解析の接続先。Cloudflare に公開するときはワークフローが `/api` にするので設定不要 |
| `SITE_URL` | （任意）独自ドメインで公開するときの URL（例: `https://example.com`）。Cloudflare に公開するときだけ使う |

プライバシーポリシー（Cookie・広告配信・アクセス解析の記載）、運営者情報、お問い合わせ、サイトマップ、構造化データ、OGP 画像は最初から用意しています。
2 ページ目以降の一覧・検索・新着一覧・掲載元別一覧・あとで読むは `noindex` にし、サイトマップからも除外しています（内容の薄いページが大量に検索結果に出ないようにするため）。

### 審査に通りやすくするために

見出しとリンクだけのサイトは、AdSense で「有用性の低いコンテンツ」と判断されやすい傾向があります。このサイトでは次の独自コンテンツを用意しています。

- AI 要約ページ（要約・要点・背景・キーワード、同じ話題を報じたほかのメディアの一覧、関連する要約）。**審査の前に、話題の記事を中心に要約を増やしておくのが最も効果的です**
- 話題のニュース（同じ出来事を報じたメディアの数で並べ、各社の報道を並べて読み比べられる）、日別まとめ
- 編集方針（`/editorial/`）: 掲載元の選び方・ランキングの決め方・AI 要約の作り方・訂正の受付・広告の扱い

また、AdSense の申し込み前に `src/config/site.ts` の運営者名・問い合わせ先を実際のものにしてください（現在の問い合わせ先は GitHub の Issue です）。

## 法的な注意（必ずお読みください）

- **登録する各サイトの利用規約を確認してください。** RSS の利用を「個人・非営利目的に限る」としているサイトや、「営利目的のサイトからのリンクは不可」としているサイトがあります（例: NHK、Yahoo!ニュースの RSS は登録していません）。広告を載せる場合は商用利用にあたります。
